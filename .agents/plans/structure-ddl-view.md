# Read-only DDL, triggers, and constraints in the structure view

## Context
`SchemaView` (`src/ui/schema_view/`) is an editable form for a table's columns, indexes, and foreign keys that diffs itself into `ALTER` statements; `TableSchema` carries exactly those three things. Missing: the definition as SQL text (`CREATE TABLE …`), triggers, and check/unique/exclusion constraints, and a definition view for views. TODO.md's "View definition viewer and editor" is covered here on the viewer side; a full editor is separate (this plan only offers "Open in query tab", where the user edits and runs `CREATE OR REPLACE VIEW`).

Decision (from user): fill the gaps only. Do not restructure `SchemaView`; add a read-only SQL panel and read-only trigger/constraint sections next to the existing forms.

## Design

### 1. Definition text — `src/db/ddl.rs` (new) + `Connection::definition`
`Connection::definition(&DatabaseObject) -> Result<String>` returns complete, runnable DDL for a table or view (table: create, then indexes, then triggers, each terminated with `;`).
- SQLite: `SELECT sql FROM sqlite_master WHERE tbl_name = ? ORDER BY (type = 'table') DESC, name` gives the original text for the table, its indexes, and its triggers, exactly as written. Skip auto-indexes (`sql IS NULL`).
- MySQL: `SHOW CREATE TABLE`/`SHOW CREATE VIEW` (exact) plus `SHOW CREATE TRIGGER` for each trigger on the table. Read the second column by position, since its name varies (`Create Table` / `Create View`).
- Postgres has no `SHOW CREATE`. Generate it in `ddl.rs` from catalog data:
  - Columns: `format_type(atttypid, atttypmod)`, `NOT NULL`, default (`pg_get_expr`), identity (`GENERATED … AS IDENTITY`), generated columns (`GENERATED ALWAYS AS (…) STORED`), collation when non-default.
  - Constraints: `pg_get_constraintdef(oid)` for primary key, unique, check, foreign key, exclusion.
  - Indexes: `pg_get_indexdef(indexrelid)` for every non-constraint index.
  - Triggers: `pg_get_triggerdef(oid)` where not `tgisinternal`.
  - Views: `pg_get_viewdef(oid, true)` wrapped in `CREATE OR REPLACE VIEW … AS`; materialised views likewise.
  - Table/column comments as `COMMENT ON` statements.
  Partitioning, inheritance, tablespaces, storage parameters, and grants are out of scope; a comment at the top says `-- Generated by Zippa DB; partitioning and grants are not included.` so nobody mistakes it for a dump.
- Identifier quoting uses `sql::quote_identifier`. The output is deterministic (sorted where the catalog has no natural order) so it diffs cleanly.
- `TableSchema` stays as is; the new read-only sections use a separate `TableExtras { checks: Vec<CheckDef>, triggers: Vec<TriggerDef> }` from `Connection::table_extras(&DatabaseObject)` so the editable forms and their diff logic are untouched. `CheckDef { name, expression }`, `TriggerDef { name, timing, events, orientation, definition }`.

### 2. UI — `src/ui/schema_view/`
- Header segmented control `Form | SQL` (two `Button`s, selected state, accessibility labels). Default is `Form` so current behaviour and tests are unchanged.
- `SQL` panel: read-only code text area configured like the query editor (same tree-sitter SQL highlighting and editor font from `settings::editor_font`), monospaced, wraps off with horizontal scroll. Buttons: `Copy`, `Open in query tab` (creates a query tab with the text, so views can be edited and re-run), `Save as .sql…` (`sql_file::prompt_for_save`). A note under the header when the form has unsaved edits: `Shows the current database definition, not your pending changes.`
- Read-only sections below the existing forms, in the same visual style as the index section header: `Constraints` (checks and, where the engine reports them, unique/exclusion) and `Triggers` (name, timing/event, and an expander showing the trigger body). No edit controls; a note that changes go through the SQL panel or a query tab.
- Views: opening a view from the sidebar's menu shows the `SQL` panel by default (a view has no editable structure); `Form` is disabled with the tooltip `Views have no editable structure`. Check what the sidebar currently does for views (`ObjectViewMode`) so this reuses the existing entry.
- Sidebar right-click on a table/view: `Copy DDL` (runs `definition` and copies, notifying `Copied definition of orders` or the error) and `Show DDL` (opens the tab on the SQL panel). Quick switcher: same two actions for the highlighted object are a follow-up.
- Reload after applying schema edits already refreshes the form; also refresh the SQL panel and extras.
- Errors: `Error: …` in words, never colour only.

### 3. Sequencing
1. `definition` for SQLite and MySQL (thin wrappers) with tests; `Form | SQL` toggle and read-only panel; `Copy`.
2. Postgres generator in `ddl.rs` with fixture-driven unit tests (pure formatting over already-fetched catalog rows), then the catalog queries.
3. `table_extras` + Constraints/Triggers sections.
4. View support and sidebar menu entries; `Open in query tab`, `Save as`.
5. Docs.

## Critical files
- new: `src/db/ddl.rs`
- edit: `src/db/{mod,schema,connection,postgres,mysql,sqlite}.rs`, `src/ui/schema_view/mod.rs` (and a small `schema_view/definition.rs` for the panel to keep the file from growing further), `src/ui/session/sidebar.rs`, `src/ui/session/tab.rs`, `src/ui/tests/schema.rs`, `TODO.md` (tick the viewer half of "View definition viewer and editor" and note the editor remains), `README.md`, `CLAUDE.md` (schema view note)
- reuse: `sql::quote_identifier`, `sql_file::{prompt_for_save,write}`, `QueryEditor` highlighting setup, `Session` "open query tab with text" path used by quick actions.

## Testing
- SQLite: `definition` of a table with an index and a trigger returns the create text, the index, and the trigger in order and skips auto-indexes; a view returns its `CREATE VIEW`; running the output on a fresh database recreates an equivalent schema (round trip through `table_schema`).
- Postgres generator: fixture rows for serial/identity, generated column, default expression, check, composite FK, partial unique index, comment; assert exact text; running it against a real server is a manual step.
- UI (SQLite): toggling to `SQL` shows the text and it is not editable; `Copy` puts the text on the clipboard; `Open in query tab` opens a tab holding it; editing a column then viewing `SQL` shows the unchanged definition and the pending-changes note; view tab opens on `SQL` with `Form` disabled; triggers and checks list.
- Manual on Postgres with a table using an enum type, a partition, and a domain: confirm the output is either correct or carries the documented omission comment.

## Risks / open questions
- Postgres fidelity is the risk: user-defined types (enums, composites, domains) are referenced but not created by the output. State that in the header comment, and list `CREATE TYPE` for enums the table uses as a stretch goal.
- `pg_get_viewdef` output is normalised, not the user's original text; that is expected and worth a line in the panel note.
- MySQL `SHOW CREATE TRIGGER` needs the `TRIGGER` privilege; on failure show the constraint/trigger sections with `Error: could not read triggers (…)` and still show the table DDL.
