# AGENTS.md

Zippa DB: cross-platform desktop database client (Postgres/MySQL/SQLite) built on GPUI (Zed's GPU-accelerated UI framework) via `gpui-kit`, with `sqlx` for database access. Early stage — see `TODO.md` for the full feature backlog and `README.md` for status/shortcuts.

Documentation for `gpui-kit` can be found here: https://gpui-kit.com/llms.txt

## Commands

```bash
cargo run              # debug build; opt-level=1 for own code, 3 for deps (see Cargo.toml) — GPUI is unusably slow otherwise
cargo run --release    # smoothest experience
cargo test              # all tests
cargo test <name>       # single test by substring match
cargo test -p zippa-db db::tests::   # module-scoped
```

macOS build needs full Xcode (not just CLI tools) for the Metal toolchain — `xcrun --find metal` must succeed. If `xcode-select -p` points at CLI tools, either `sudo xcode-select -s /Applications/Xcode.app` or prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.

There is no separate lint command configured beyond `cargo clippy` / `cargo fmt` (standard Rust tooling, not wired into any script here).

## Architecture

**Two async worlds, bridged by a channel.** GPUI has its own executor; `sqlx` needs a Tokio reactor. `src/db/runtime.rs` owns a lazily-initialized, dedicated 2-thread Tokio runtime. All database work is submitted via `runtime::spawn(future)`, which returns a `oneshot::Receiver` that a GPUI `cx.spawn` task awaits. Never call sqlx directly from a GPUI view — always go through this runtime. Under `#[cfg(test)]`, `spawn` instead runs the future to completion inline on the calling thread (GPUI's single-threaded test scheduler aborts if woken from another thread), so tests get deterministic results without touching the real background runtime.

**Engine abstraction (`src/db/`).** The split is by concern, not by engine: `config.rs` defines `Engine` (Postgres/MySql/Sqlite), `SafetyMode`, and `ConnectionConfig` (serializable, no password); `connection.rs` defines `Connection` (holds a `Pool` enum wrapping the sqlx pool type plus the password in memory — never persisted) and the generic `fetch_all`/`execute_with` behind it; `sql.rs` owns quoting and bind placeholders for generated statements. `mod.rs` is a module map and re-exports all of it, so `crate::db::Connection` and friends still resolve. Each engine's specifics — pool setup, connection string building, SQL for listing databases/objects, and decoding a `sqlx::Row` cell to a display `String` — live in `postgres.rs` / `mysql.rs` / `sqlite.rs` behind a common shape (`connect`, `DATABASES_SQL`, `OBJECTS_SQL`, `cell`). `Connection::run_query` dispatches on the pool variant into a shared generic `fetch_all` that works over any `sqlx::Database`. To add a capability across engines, add the shared entry point in `connection.rs` and implement per-engine in the three sibling files.

**Values are text, both ways.** A cell is a display `String`, so each engine's `cell` maps its driver types to a text form the same server will read back unchanged — `1` for a boolean (as MySQL and SQLite already store one), `2024-01-02 03:04:05`, `03:04:05+02:00`, `1 day 02:03:04`, `{1,2,3}`. Postgres decodes one arm per type through the `value!` macro in `postgres.rs`, which covers `T` and `T[]` together (an array is rendered by `array_literal`, which quotes only the elements Postgres would not read back bare); `xml` has no sqlx mapping but its binary encoding *is* the document, so it is read straight off the raw bytes. `timestamptz` arrives as an instant rather than text, so it is shown in the local zone with the offset spelled out. On the way back in, every parameter is bound as text and `typed_placeholder` makes it acceptable: Postgres casts to the column's type, except where a bare driver type name has lost a width (`CHAR` is `character(1)`, `BIT` is `bit(1)`) and `cast_target` substitutes the width-free relative; MySQL needs no cast except for `BIT`, whose digits it would otherwise store as their own bytes. Anything still undecodable comes back as a `query::unsupported` stand-in, which `query::is_placeholder` recognises so the grid will not write it back.

**Persistence split.** `db/store.rs`: connection *metadata* goes to `connections.json` in the OS config dir; passwords go to the OS keychain via the `keyring` crate, keyed by connection `Uuid`. Never write a password into the JSON store. `ConnectionConfig::safety` (a `SafetyMode`), `tag`/`color` (a `TagColor`, the per-connection environment label), and `last_connected` all ride along in that metadata; each is `#[serde(default)]` so older files read back as untagged and careful.

**Workspace state.** `workspace_state.rs` lays the window's tabs out beside the connections in `workspace.json` — connection ids, per-tab buffers, and the active tabs, never a password. `Workspace::new` reopens every connection the file names (through `Welcome::open`, the same path a card click takes) and `Session::restore` rebuilds each one's tabs; `Workspace::snapshot` records the live ones, folding in a connection still reconnecting so a failed start does not erase it. State is written at **checkpoints**, not on keystrokes: `SessionEvent::Changed` (from `install`/`forget`/`close_tab_now`/`touch`/`send`/`write`/`switch_database`) and workspace tab changes ask for a save, and `Workspace::flush_state` writes synchronously on quit for the text typed since the last one; an unchanged snapshot is skipped. Query buffers are stored as plaintext, like the connection metadata.

**Safety modes.** `SafetyMode` is one scale per connection: `ReadOnly`, `ConfirmWrites`, `Staged` (default), `AutoApply`. `ReadOnly` is enforced twice — the pool is opened read-only per engine (`default_transaction_read_only` on Postgres, `SET SESSION TRANSACTION READ ONLY` via `after_connect` on MySQL, `read_only(true)` on SQLite), and `db/statement.rs` classifies the user's SQL client-side so `Connection::run_query`/`execute` can refuse it with a message naming the statement. That classifier is an allowlist over a comment- and quote-aware scanner: anything it cannot recognise as a read counts as a write. `ConfirmWrites` holds the built statement in the UI — `Session::run` parks the buffer in `Status::Confirm` for the status bar to answer, `TableView` parks its generated `UPDATE`s in `Confirming` for the preview panel.

**UI is a view tree of GPUI entities (`Entity<T: Render>`), wired with events, not callbacks.** `app::Workspace` is the root: it owns a tab per open connection, each holding either `ui::welcome::Welcome` (connection manager) or `ui::session::Session` (an open connection). `WelcomeEvent::Connected` turns the tab it came from into a session and `SessionEvent::Disconnected` turns it back, both via `cx.subscribe_in`; closing a tab drains that connection's pool. Tabs therefore nest: connections on the workspace bar, queries and tables on the session's own bar. `ui::welcome` is a directory — `mod.rs` is the launcher (searchable cards, most-recently-connected first), `card.rs` renders one connection, and `editor.rs` is the `ConnectionEditor` dialog the launcher opens; it emits `EditorEvent` and the launcher reacts. `Session` is a directory: `mod.rs` is the view, `tab.rs` holds `SessionTab`/`TabContent`/`Status` (either a `QueryEditor`+`DataGrid` pair or a `TableView` opened from the sidebar), `sidebar.rs` holds the object list and the regex filter over it (from `Connection::objects`) — that is where TODO.md's schema tree goes — and `test_support.rs` holds the `#[cfg(test)]` reach-ins. Follow the same pattern for new screens/panels: a child entity that emits its own event enum, subscribed to by its parent rather than reaching into parent state directly.

**Keybindings are centralized in `src/keymap.rs`**, bound once at startup, using GPUI's `secondary` modifier (Cmd on macOS, Ctrl elsewhere) so all shortcuts are automatically platform-correct. Actions are declared with the `actions!` macro next to the view that handles them (e.g. `NewTab`/`CloseTab` in `session.rs`, `RunQuery` in `query_editor.rs`) and bound to specific GPUI context paths (e.g. `"QueryEditor > Input"`) — check existing bindings' context-path comments before adding new ones, since GPUI resolves the most specific matching context.

**Grid editing.** `ui::data_grid` is a directory: `mod.rs` is the view and the commands its owner drives it with, `delegate.rs` is `ResultDelegate` — the result plus everything staged on top of it, which is what the table component asks for cells — `format.rs` lays one value out for reading, and `layout.rs` sizes the columns. The delegate's fields and methods are `pub(super)` because the view reaches into them; keep new overlay state there rather than in the view. `DataGrid` keeps four overlays on top of the result it was handed: `edits` (typed cells, keyed by result row and column), `drafts` (rows being built by hand, each holding only the columns typed into, written by an `INSERT` so untouched columns keep the server's default), `deletions` (result rows marked to go), and `rows_selected` (a row-level selection swept with the mouse, separate from the table component's own selected cell). Every pending change is marked where it is: an edited cell is tinted green *and* underlined, a new row is blue, a deleted row is red and struck through. Colour is never the only cue — the underline and the strike-through are what a colour-blind user reads, so keep that pairing when adding a state. The grid never writes: it emits `GridEdit`, and `TableView` turns the overlays into `UPDATE`/`INSERT`/`DELETE` when the changes are applied (`Cmd+S`, or the footer's Apply button). A deleted row's edits are dropped rather than written. On a `ConfirmWrites` connection the footer panel asks about the change counts — the rows on screen already show what will happen, so the SQL is not listed.

**Selection, focus, and keys.** The grid works in cells: the table is built with `cell_selectable(true)` but `row_header(false)`, `row_selectable(false)`, and `loop_selection(false)`. Rows are picked out by the grid's own checkbox column, so the table's row-header strip and its row selection *mode* are off — two ways to select a row that meant different things is what made the highlight drift, and the table's row mode also left `selected_cell` unset, which is what edit, copy, and view-value read. `SelectRow` (which the table still falls back to when a key arrives with nothing selected) and a `SelectCell` on the checkbox column are both turned into a cell on the first *value* column in `on_table_event`, so the selection never rests where there is nothing to act on and an arrow at the edge stays put instead of reappearing on the other side.

The row menu carries the same commands: "Copy value" for the cell the click landed on (which is not always the selected one) and "Copy N rows" while rows are picked, each with `.action(Box::new(CopyValue))` on whichever one the keystroke would do, so the shortcut is shown beside it.

Two row states, told apart: `focused_row` is where the keyboard is — a bar down the row's leading edge, plus a weak tint and the table's own border on the selected cell — and `rows_selected` is what a row command acts on (the full selection tint, plus a checked box). The bar is there because the tint alone cannot be relied on: a theme that sets no `table.*` colours inherits `list.active.background`, which several of the bundled dark ones make about an eighth opaque, so `readable` puts a floor under the alpha and the bar carries the focus regardless. `render_tr` also blends each tint onto the row's own backdrop by hand (`Hsla::blend`, stripe included) — a background set there *replaces* the one the table painted rather than covering it, so a translucent tint painted straight on drops the stripe and reads as an unmarked row. `Cmd+C` copies the picked rows as tab-separated lines, or the selected cell when none are picked, and `Cmd+Shift+C` the same rows with a header line; `Space` picks the focused row out, `Shift+↑`/`↓` extends from it, `Cmd+A` takes them all and `Cmd+Shift+A` (or `Escape`, which the table answers with `ClearSelection`) puts them back. With the pointer: the box, `Shift`-click for the range, `Cmd`-click anywhere in the row to toggle it, and a drag down the boxes to sweep a range (`sweeping` says whether the drag is adding or removing; the grid root ends it on mouse up). The row-level modifier clicks live in the same capture-phase handler as the menu row, because the table stops a click on a cell before it can bubble; the box itself therefore ignores a `Cmd`-click, which that handler has already answered.

Finishing a cell editor with `Enter` or giving up with `Escape` hands the keyboard back to the table, so the arrows work straight away; a blur does not, since the user put the focus somewhere themselves. Clicking a pick box does the same — the box takes the focus on mouse down, and it is handed back in the click.

Whoever hands a table tab the focus has to land on the grid's table, since that is the node the keys are bound under: anything above it swallows every keystroke. So `DataGrid` and `TableView` both implement `Focusable` by answering with the table's handle, and `SessionPanel::focus_handle` returns it for a `Table` tab the way it returns the editor for a query one. That is what makes the arrows work after the value dialog closes (`Workspace::focus_active` runs on `Dismissed`), and on a tab that has only just been opened. `PopupMenu` restores the focus itself, so the row menu needs nothing.

The row menu is one `.context_menu(...)` on the grid's own root element, and the row it is about is recorded by a **capture-phase** `capture_any_mouse_down` on each row (`render_tr`). That is deliberate: with `cell_selectable(true)` the table answers a right click on a cell itself, clearing `right_clicked_row` and stopping propagation, so `TableDelegate::context_menu` is left unimplemented — the table's own menu stays empty and an empty `PopupMenu` is never shown. Do not move the menu back onto cells or rows: a per-cell menu misses the row-header column and the space beside the last column, and only the grid-root element is stable enough for the first right click to open it.

**Value dialog.** `ui::value_dialog` shows one cell's value over the whole window (`DataGrid::view_cell`, `Cmd+Shift+V`, "View value" in the row menu, or a double click on a value a cell cannot show — see `data_grid::needs_a_window`: several lines, JSON, binary, or over 200 characters). A cell has no window to build a text box with, so `view_cell` leaves a `ValueRequest` in a global and `Workspace::take_value_dialog` builds the `ValueView` while it renders; the view emits `Dismissed` when it is done and the workspace drops it. `data_grid::format_value` decides the layout: JSON is laid out over several lines with `serde_json`, and the `<3 bytes>` / `<GEOMETRY>` stand-ins say the value was never read back. The dialog takes a `Save` closure from whoever opened it — `None` for a value that cannot be written back, which also makes the text box read-only — and saving (`Cmd+Enter`) stages the text in the grid like typing into the cell does. `Escape` closes without saving.

The cells also stop a right click in the bubble phase (`stop_right_click` in `delegate.rs`). The table marks the cell a right click landed on and outlines it, and clears that mark when the next click lands outside — but it only registers that click-out handler for a right click on a *row*, so a cell's outline stayed on screen for good, including on the cell a value was viewed from. Stopping the click first means the table never takes the mark: its own handler stops the event one listener later anyway, and the grid's menu is unaffected because `ContextMenuExt` registers its listener after painting its subtree, which puts it first in the bubble phase — ahead of both. There is no test: a right click that reaches the menu builds a `PopupMenu`, which the harness then reports as a leaked entity (see the note in `ui/tests/mod.rs`).

Two ordering rules make the row menu work, both learned the hard way: the cell a right click landed on is recorded by a **capture-phase** handler in `render_td` (a `TableEvent` from the table reaches its owner *after* the menu is built, so the menu would be a click behind), and the row's own capture handler clears that cell first, so a click beside the cells is about the row alone.

**Filtering.** `ui::filter_bar::FilterBar` is the bar above a table view: one line per filter, each a column dropdown, an `Operator`, and a value box (hidden for `IS NULL` / `IS NOT NULL`). The bar only *describes* filters — `TableView::where_clause` turns them into SQL, since it owns the engine, the column types, and the rest of the statement. Values are bound as parameters through `Connection::run_query_with`; the exception is `IN` / `NOT IN`, whose value is pasted in as written so a subquery can filter the table. A filter change re-reads from the first page and goes through the same staged-edit guard as paging and sorting.

**Running SQL.** `db/statement.rs` splits a buffer into statements with their byte ranges (`split`, `at_cursor`), which is what lets `Cmd+Enter` send only the statement the caret is in — a selection runs verbatim instead — and `Cmd+Shift+Enter` run the buffer through `Connection::run_script`, one statement at a time. Every run comes back as a `Vec<QueryResult>`, so a tab keeps `results` plus which one the grid shows and puts a result bar above the grid when there is more than one. `fetch_all` reads rows and `rows_affected` from the same stream, so `QueryResult::affected` is filled in for writes and `summary()` can say "2 rows affected in 3 ms". `runtime::spawn` hands back a `Task` whose `abort_handle` the tab holds; `Cmd+.` aborts it, which drops the work on the Tokio runtime and resolves the awaiting side with an error the session reports as "Cancelled".

**Query results** flow through `db::query::QueryResult` (columns + rows of `Cell` + elapsed time) and render via `ui::data_grid::DataGrid`, a virtualized read-only grid. `ui::table_view::TableView` builds on top of it for the sidebar's "open table" flow, adding paging/limit/sort by generating and re-running SQL rather than manipulating an in-memory result set. Every statement it generates — the page, the `where` clause, the `UPDATE`/`INSERT`/`DELETE` — lives in `table_view/sql.rs` as `impl TableView`, apart from the rendering; put DDL generation there too.

**Exporting.** `db/export.rs` lays a result out as CSV, TSV, JSON, Markdown, or SQL `INSERT` — plain text, no window and no database. A cell the driver could only describe (`query::is_placeholder`, `<3 bytes>`, `<GEOMETRY>`) is written `NULL` in every format, and `Rendered::skipped` counts them so the footer can say so. JSON is typed by the driver's column type: numbers and booleans go bare (an integer past 2^53 becomes a string, which JavaScript can hold), a `json`/`jsonb` value is embedded, and anything else is a string; SQL writes a number bare only where its column's type is numeric and quotes the rest, with `db::sql::quote_literal_for` doubling a backslash on MySQL (a backslash is an escape there and nowhere else). `TableView::select_sql(paged: false)` keeps the filters and sort but drops `limit`/`offset`, so a table export is every row the view is showing rather than the page in hand; `DataGrid::snapshot(Scope::Picked, cx)` gathers the picked rows through the delegate's own `cell`, so a staged edit goes out as it stands. Both ask for a path first (`sql_file::prompt_for_save`, extension-aware) and write on GPUI's background executor. The grid's row menu offers an export only when its owner named a table (`DataGrid::set_table`) — the table view does, since only it has a name for the `INSERT`.

**Importing.** `db/import/` runs a SQL dump back into the connection: `mod.rs` is the runner, `reader.rs` detects compression and counts bytes for progress, and `splitter.rs` streams the dump into statements. `Connection::import_dump` checks out one dedicated connection so the session state a dump sets up — `SET`, `USE`, `PRAGMA`, temporary tables — survives the whole run; that connection is closed rather than returned to the pool, so a cancelled import cannot leave a half-open transaction behind. Input is decompressed by magic bytes (gzip, bzip2, zstd) and split one statement at a time, so a dump is never held in memory: `COPY ... FROM stdin` is streamed straight into `copy_in_raw`, MySQL's `DELIMITER` is honoured and dropped, SQLite trigger bodies keep their semicolons, and psql's `\` meta-lines are skipped. The dump's own top-level `BEGIN`/`COMMIT` are replaced by the runner's own transaction control, and the `OnError` policy decides what a failure does — `Stop` keeps what ran, `Rollback` wraps the run in one transaction and undoes it (Postgres and SQLite; MySQL falls back to `Stop` with a note, because its DDL commits itself), and `Continue` skips the statement and logs it. `ui/import_dialog.rs` is the dialog the sidebar button, the File menu, and `Cmd`/`Ctrl`+`Shift`+`I` open: it pre-flights the file (compression, size, a dialect mismatch, a count of statements that drop or clear data) and blocks a read-only connection rather than pretending to try, then shows a labelled progress bar and, at the end, the summary and error list. `Session` holds the dialog, so `Cmd`/`Ctrl`+`.` cancels an import the same way it cancels a query.

**Copying.** The grid writes the clipboard itself, so a copy works the same in a table tab and a query tab. `DataGrid::snapshot(scope, cx)` is the one place that decides what a copy takes — `Scope::Picked` (the picked rows, or every row when none are picked), `Scope::All`, or `Scope::Column` for the single-column shapes — and hands back the columns, driver types, and cells as they stand, staged edits included. `Cmd+C` keeps its old cell-or-rows behaviour; `Cmd+Shift+C` is TSV with a header (`CopyWithHeaders`), and the rest live in the row menu's `Copy as` submenu: CSV, JSON, a Markdown table, SQL `INSERT`, and the single-column `values` / `in_list` shapes (`('a', 'b', 3)`, typed and with NULLs dropped). Items that need something the grid does not have are hidden (SQL without a table name) or disabled (column shapes without a column) rather than left to fail. The payload is capped — 100,000 rows or 50 MB — and the notice says `Copied first 100,000 of 250,000 rows` rather than pretending it is whole. Every copy emits `Copied`, which the table view shows in its footer `notice` and a query tab shows through `Status::Done` in its status bar, the same place a run's summary goes.

**Schema editing.** `ui::schema_view/` is the structure tab: `mod.rs` is the form (editable columns, indexes, and foreign keys, diffed against what was loaded), `sql.rs` generates the `ALTER TABLE` statements for Postgres and MySQL, and `rebuild.rs` generates SQLite's table rebuild. `Change` is what gets staged: `Statements` run one at a time through `Connection::execute` as before, while `Rebuild` is one atomic procedure via `Connection::rebuild_table` — one dedicated connection, foreign keys off around a transaction (`PRAGMA foreign_keys` is a no-op inside one), and `PRAGMA foreign_key_check` before it commits, so a rebuild that breaks a relationship rolls itself back. SQLite's plain `ALTER TABLE` can only rename, add, and drop, so a type, nullability, or default change, or an add/drop of a primary or foreign key, becomes a copy-and-swap (sqlite.org's "Making Other Kinds Of Table Schema Changes"): `RebuildSource` (read alongside `TableSchema` by `Connection::rebuild_source`) carries the table's stored `CREATE TABLE` plus the stored text of its explicit indexes, triggers, and views; the generator restates columns, the primary key, `UNIQUE` constraints (SQLite's auto-indexes have no SQL of their own), and foreign keys, copies the rows with renames mapped, then replays the indexes/triggers/views (rewriting identifiers for a renamed column, and recreating only-renamed views). A table whose definition holds something `TableSchema` cannot model — a `CHECK`, `COLLATE`, generated column, `AUTOINCREMENT`, or `WITHOUT ROWID`/`STRICT` — is refused rather than silently changed; so is dropping a column an index, trigger, or view still reads. The rebuild connection runs `PRAGMA legacy_alter_table = ON` so the rename does not choke on a view left dangling by the `DROP TABLE` in the middle of the procedure.

**Settings and discoverability.** `settings::Settings` is one serde struct behind a GPUI global; `settings::update` is the only way to change it and it writes the file, re-applies the theme, and refreshes every window. `apply` also runs `apply_scrollbars`, because `Theme::change` rebuilds the projection the scrollbars read: with `always_show_scrollbars` (the default) the mode is `ScrollbarMode::Always`, since a wide result is scrolled sideways by dragging its bar and a bar that fades out cannot be grabbed with a mouse. Every setting needs a way in that is not a keystroke — the settings window has a gear in the title bar beside the shortcut.

**Accessibility rules of thumb.** An icon-only `Button` has no name for a screen reader unless it is given one, so every one of them carries `.accessibility_label(...)`; the same goes for a bare `Checkbox`. Where an action has a keybinding, use `.tooltip_with_action(text, &Action, Some("Context"))` rather than `.tooltip(text)` — the component renders the bound key, which is how a shortcut becomes discoverable. Anything clickable should be a `Button` rather than a `div` with `on_click`, so it is reachable by tab and answers the keyboard — or, for a list of items rather than a single control, `gpui-kit`'s `Tree`/`TreeState` (`ui::session::sidebar`'s object list is the worked example), whose rows carry their own ARIA role and label and answer arrow keys without either side wiring it by hand. State told by colour must also be told some other way: errors say `Error: …` in words, staged cells are underlined, deleted rows are struck through.

**Tests.** `src/ui/tests/` is one file per area (`editing`, `rows`, `navigation`, `paging`, `safety`, `filters`, `running`, `session`, `sorting`, `layout`, `files`, `workspace`, `value_dialog`, `preferences`), with every shared fixture in `mod.rs` and each file opening with `use super::*;`. Put a new test in the file that matches what it is about, and a new fixture in `mod.rs` — a helper that only one file uses still belongs there, so the next area can find it.

### Accessibility

* Every icon-only button and checkbox carries a name for a screen reader
* Tooltips show the keystroke an action is bound to, so shortcuts are discoverable from the UI
* The sidebar's object list is reachable by keyboard
* Nothing is told by color alone: errors say so in words, staged cells are underlined, deleted rows are struck through
* The grid's per-row pick boxes are not tab stops — one per row would mean tabbing through a page of them — so `Space`, `Shift`+arrows, `Cmd+A`, and `Cmd+Shift+A` are what pick rows from the keyboard; the header's "select every row" box is still tab-reachable
* Known deviation: a dock panel's own `+` (beside its tab strip) is not tab-reachable — `gpui-kit`'s dock forces `tab_stop(false)` on toolbar buttons. `Cmd+T` is bound and named in the button's tooltip, and the workspace toolbar's `new-query` button (`src/app.rs`) is still tab-reachable, so a new query tab is always reachable by keyboard some other way.
