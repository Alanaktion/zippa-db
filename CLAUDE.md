# AGENTS.md

Zippa DB: cross-platform desktop database client (Postgres/MySQL/SQLite) built on GPUI (Zed's GPU-accelerated UI framework) via `gpui-kit`, with `sqlx` for database access. Version 0.1 — see `README.md` for features and shortcuts, GitHub issues for the backlog (`.agents/plans/` holds implementation notes for items that need them, removed once the work ships), `AUDIT.md` for known defects in shipped code, and `CHANGELOG.md` for what each release changed.

Documentation for `gpui-kit` can be found here: https://gpui-kit.com/llms.txt

This file records the architecture and the non-obvious rules; the code is the source of truth for file layout, names, and key bindings.

## Commands

Building needs a recent stable Rust (1.95 or newer — GPUI uses `std::hint::cold_path`); CI tracks the latest stable.

```bash
cargo run              # debug build; opt-level=1 for own code, 3 for deps (see Cargo.toml) — GPUI is unusably slow otherwise
cargo run --release    # smoothest experience
cargo test              # all tests
cargo test <name>       # single test by substring match

# Live tests against real MySQL/Postgres (#[ignore]d by default):
./script/test-db up         # start containers from compose.yaml, wait until healthy
cargo test -- --ignored live_
./script/test-db down       # stop them
```

`ZIPPA_TEST_MYSQL_URL`, `ZIPPA_TEST_POSTGRES_URL`, and `ZIPPA_TEST_POSTGRES_YEN_URL` point the live tests at different servers; the defaults match what `compose.yaml` starts.

macOS build needs full Xcode (not just CLI tools) for the Metal toolchain — `xcrun --find metal` must succeed. If `xcode-select -p` points at CLI tools, either `sudo xcode-select -s /Applications/Xcode.app` or prefix commands with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.

CI (`.github/workflows/ci.yml`) runs `./script/linux`, then `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test`; run the same three before pushing. `Cargo.toml`'s `[lints]` denies `unsafe_code` (the one `sqlite3_get_autocommit` call carries an `allow`) and warns on `unwrap`/`expect` outside tests (`clippy.toml`), so a justified one needs `#[allow(clippy::expect_used, reason = …)]`. A separate `deny` job runs `cargo deny check` against `deny.toml` (advisories, licences, sources; duplicate versions only warn) — an ignored advisory needs a `reason`. The `#[ignore]`d live tests run separately in `.github/workflows/live-tests.yml` (nightly, on push to `main`, and on manual dispatch).

## Architecture

**Two async worlds, bridged by a channel.** GPUI has its own executor; `sqlx` needs a Tokio reactor. `src/db/runtime.rs` owns a lazily-initialized, dedicated 2-thread Tokio runtime. All database work is submitted via `runtime::spawn(future)`, which returns a `oneshot::Receiver` that a GPUI `cx.spawn` task awaits. Never call sqlx directly from a GPUI view — always go through this runtime. Under `#[cfg(test)]`, `spawn` instead runs the future to completion inline on the calling thread (GPUI's single-threaded test scheduler aborts if woken from another thread). A `Task` is detached when dropped unless built with `.abort_on_drop()`, which work owned by a view that can close uses so it does not outlive it.

**Engine abstraction (`src/db/`).** The split is by concern, not by engine: `config.rs` (`Engine`, `SafetyMode`, `ConnectionConfig` — serializable, no password), `connection.rs` (`Connection`: a `Pool` enum over the sqlx pool types plus the password in memory, and the generic `fetch_all`/`execute_with`), `sql.rs` (quoting and bind placeholders for generated statements). Each engine's specifics — pool setup, connection strings, listing SQL, decoding a `sqlx::Row` cell to a display `String` — live in `postgres.rs` / `mysql.rs` / `sqlite.rs` behind a common shape. To add a capability across engines, add the shared entry point in `connection.rs` and implement it per engine in the three sibling files. `db/` never depends on GPUI. Logic that can be pure (`catalog::search`, `completion`, `statement`, `filter_variables`, `render_postgres_table`) is, so it is unit-tested without a database or a window.

**Values are text, both ways.** A cell is a display `String`, so each engine's `cell` maps driver types to a text form the same server reads back unchanged (`1` for a boolean, `2024-01-02 03:04:05`, `1 day 02:03:04`, `{1,2,3}`; `timestamptz` shown in the local zone with the offset). On the way in, every parameter is bound as text and `typed_placeholder` makes it acceptable: Postgres casts to the column's type (substituting the width-free type where a bare driver name lost a width, `cast_target`); MySQL needs no cast except `BIT`. Anything undecodable comes back as a `query::unsupported` stand-in that `query::is_placeholder` recognises — given the column's type, since `<TYPE>` must name it (a real `<nil>` in a text column is a value) — so the grid will not write it back and exports write `NULL`. The one deliberate exception is a staged binary value: the value dialog stages a file's bytes as hex text, still bound as text, and the server decodes it (`sql::binary_placeholder`), so no binding path has to learn a new type.

**Persistence.** Connection *metadata* goes to `connections.json` in the OS config dir; passwords go to the OS keychain (`keyring`) keyed by connection `Uuid`; the SSH password/passphrase is a second entry (`{id}/ssh`). **Never write a secret into a JSON file.** Rules every JSON file (`connections.json`, `workspace.json`, `settings.json`, `saved_queries.json`, `dashboards.json`) follows:
- Written through `store::write_restricted` (mode `0o600` from the first byte, since a query buffer may hold a pasted secret), and `store::write_atomic` on top (temp file + rename, with a `store::ticket()` drawn when the snapshot was taken so a stale background checkpoint cannot land after the quit-time flush).
- Read through `store::load_json`, which moves an unparseable file aside to `<name>.unreadable` rather than letting the next save replace it with an empty list.
- New fields are `#[serde(default)]` so older files load; unknown fields are skipped.
- Shared lists (`SavedConnections`, `SavedQueries`, `Dashboards`) are one GPUI global each, loaded once and changed only through their one entry point, so two launchers/windows never save over each other. Write the in-memory list, never load-mutate-save against the file (that raced the editor's own save once).

Connection options that ride in the metadata: `ssl` (libpq's mode scale; the mode is always set explicitly on the driver so `PGSSLMODE` in the environment cannot change a saved connection; file paths are kept whatever the mode but only sent from `Require` up), `ssh` (see below), `safety`, `color`, `statement_timeout`, `agent_access`. `db/tunnel.rs`'s `Tunnel` (russh with `ring`, so no C toolchain) listens on a loopback port and carries each pool connection over its own `direct-tcpip` channel; `Connection::open_with` points the driver at `127.0.0.1:port` while `Connection::config` keeps the host the user saved. The tunnel is an `Arc` on `Connection`, reopened by `with_database` if the jump host dropped it, and closed with the last clone. For SQLite the same `ssh` settings mean the file is on that host (`db/remote.rs`'s `RemoteFile`, over `russh-sftp`): it is downloaded to an owner-only cache directory and the pool opens that copy, while `config.database` keeps the remote path. `Connection::upload` sends a `VACUUM INTO` snapshot (consistent even mid-transaction; WAL mode restored) to a hidden sibling and renames it into place (`posix-rename@openssh.com`), refusing a file with a live `-wal`/`-journal`, and answering `Upload::ServerChanged` when the host's size, mtime, or 100-byte header differ from the last sync so the UI can warn before a forced upload. Un-uploaded changes are a file-stat comparison (`has_unuploaded_changes`), asked about on close and quit; a copy with changes is left in the cache rather than deleted. Host keys are checked against `~/.ssh/known_hosts` (unknown recorded, changed refused). The editor hands secrets on as `store::SecretEdits` (`None` = untouched box, keep what is stored).

**Workspace state.** `workspace.json` records connection ids, per-tab buffers, and active tabs — never a password. `Workspace::new` reopens every connection through `Welcome::open`, and `Session::restore` rebuilds each one's tabs. State is saved at **checkpoints** (`SessionEvent::Changed`, workspace tab changes), not on keystrokes, plus a synchronous `Workspace::flush_state` on quit; an unchanged snapshot is skipped. A connection still reconnecting is folded into the snapshot so a failed start does not erase it. A dashboard restored at startup does not run.

**Connection health.** Every pool comes from `connection::pool_options` (10 s `acquire_timeout`). The shared entry points on `Connection` and `Dedicated` pass their errors through `health::plain`, which turns an I/O error, pool timeout, closed pool, or Postgres shutdown code into a `ConnectionTrouble` whose message points at Reconnect (no source, so `{error:#}` never appends driver text). `Reconnect` is `Session::reconnect`: the same `with_database` + `adopt_connection` path as a database switch, so tabs, buffers, and the console survive. `statement_timeout` is applied as each pooled connection starts and is not offered for SQLite.

**Safety modes.** `SafetyMode` is one scale per connection: `ReadOnly`, `ConfirmWrites`, `Staged` (default), `AutoApply`. `ReadOnly` is enforced twice — the pool is opened read-only per engine, and `db/statement.rs` classifies SQL client-side so `Connection` entry points refuse a write through one `refuse_read_only` ("this connection is read-only, so …"). The classifier is an allowlist over a comment- and quote-aware scanner told the `Engine` (every `statement::` entry point takes one): anything it cannot recognise as a read counts as a write. `ConfirmWrites` leans on the classifier alone (no read-only server session), so `WRITING` includes `INTO` to catch `SELECT … INTO`/`INTO OUTFILE`. `ConfirmWrites` holds the built statement in the UI (`Status::Confirm` for a query tab, `Confirming` for table edits).

`AutoApply` on a connection that reads as production (red, or named "prod") is warned about by both the connection editor and the launcher's card click, from the one `is_risky_auto_apply`. The gate sits above `connect_saved` on purpose: a session restored at launch calls `connect_saved` directly and must not answer a stack of confirmations.

**UI is a view tree of GPUI entities (`Entity<T: Render>`), wired with events, not callbacks.** `app::Workspace` is the root, with a tab per open connection holding either `ui::welcome::Welcome` (launcher) or `ui::session::Session` (an open connection); `WelcomeEvent::Connected` / `SessionEvent::Disconnected` swap them via `cx.subscribe_in`, and closing a tab drains that connection's pool. Tabs nest: connections on the workspace bar, queries/tables/tools on the session's own bar. Follow the same pattern for new screens: a child entity that emits its own event enum, subscribed to by its parent rather than reaching into parent state. `Session` and the larger views (`data_grid`, `table_view`, `schema_view`, `query_editor`) are directories split by concern, one `impl` block per file, with a `test_support.rs` holding the `#[cfg(test)]` reach-ins so a `_for_test` method never sits in production code. A new connection tool is one arm per match in `session/tool.rs` (`Tool` / `ToolView`), not a method per `SessionPanel`. The session reads the whole schema into a `catalog` snapshot once (reloaded by `Refresh` and on a database switch), shared with every query tab as `ui::completion::SharedCatalog` so open tabs see a reload with no event.

**Session tabs.** Tabs are dock panels, so a tab's commands live on what the panel draws and are emitted as `SessionPanelEvent` for the session to resolve — the panel cannot read its siblings, since reading its `TabGroup` while the group is drawing it panics. `CloseScope` distinguishes along-the-strip closes (`Others`/`ToTheRight`, in the dock's order) from session-wide ones (`QueryTabs`/`TableTabs`); a set closes through one question. Closing a tab must hand the active tab *and* the keyboard to the panel the dock puts in its place (`Session::adopt_dock_active`), since the dock drops focus with the removed panel.

**Keybindings and menus.** All bindings are in `src/keymap.rs`, using GPUI's `secondary` modifier so they are platform-correct. Actions are declared with `actions!` next to the view that handles them and bound to context paths — check existing context-path comments first, since GPUI resolves the most specific match. `src/menu.rs` builds the OS menu from the same actions, so a menu item is another way to reach a binding, not a second implementation; put a new action in a menu as well as the keymap (its tests fail otherwise). A command with no shortcut worth spending is listed in the `unbound` allowlist of `every_menu_item_answers_to_a_keystroke`. In-view menus click through to the view directly and set `.action(...)` on items only so the shortcut shows. On Linux/Windows `AppMenuBar` draws the menus in the title bar. A dialog opened with `keyboard(false)` declares its own close action and binds `escape` to it on the body's key context in the keymap — declaring the action without the binding leaves `Escape` doing nothing.

**Grid editing.** `ui::data_grid` shows a result plus four overlays on top of it, all kept in `ResultDelegate` (keep new overlay state there, not in the view): `edits` (typed cells), `drafts` (rows being built by hand; only typed columns are written, so untouched columns keep the server default), `deletions`, and `rows_selected`. Every pending change is marked by more than colour — edited cells are green *and* underlined, new rows blue with typed values underlined, deleted rows red and struck through; keep that pairing for any new state. The grid never writes: it emits `GridEdit`, and `TableView` turns the overlays into `UPDATE`/`INSERT`/`DELETE` on apply. A deleted row's edits are dropped.

**Grid selection, focus, and keys.** Hard-won rules:
- The table is built `cell_selectable(true)` with `row_header`, `row_selectable`, and `loop_selection` off. Rows are picked by the grid's own checkbox column; two row-selection mechanisms made the highlight drift, and the table's row mode left `selected_cell` unset, which edit/copy/view-value read. `SelectRow` and a `SelectCell` on the checkbox column are redirected to the first value column in `on_table_event`.
- `focused_row` (where the keyboard is: a leading bar plus weak tint) is separate from `rows_selected` (what a row command acts on). The bar exists because a theme with no `table.*` colours can inherit a near-transparent tint; `render_tr` blends tints onto the row's backdrop by hand because a background set there *replaces* the table's own (stripe included).
- Finishing a cell editor with `Enter`/`Escape` hands the keyboard back to the table; a blur does not. Whoever hands a table tab focus must land on the grid's table, the node the keys are bound under — hence `DataGrid`/`TableView` implement `Focusable` with the table's handle and `SessionPanel::focus_handle` returns it for table tabs.
- The row menu is one `.context_menu(...)` on the grid root; do not move it onto cells or rows (a per-cell menu misses the row header and the space past the last column). Two ordering rules: the clicked row and cell are recorded by **capture-phase** handlers (`render_tr`/`render_td`), because a `TableEvent` reaches the owner *after* the menu is built and the table stops cell clicks before they bubble; and cells stop a right click in the bubble phase (`stop_right_click`) so the table never leaves a stuck outline. A right click that reaches the menu leaks a `PopupMenu` in the test harness, so it has no test (see `ui/tests/mod.rs`).

**Value dialog.** `ui::value_dialog` shows one cell over the whole window. A cell has no window to build a text box with, so `view_cell` leaves a `ValueRequest` in a global and `Workspace::take_value_dialog` builds the view during render; the view emits `Dismissed`. It takes a `Save` closure from its opener — `None` for an unwritable value, which also makes it read-only — and saving stages the text in the grid like typing into the cell.

**Filtering and table reads.** `FilterBar` only *describes* filters; `TableView::where_clause` builds the SQL (it owns the engine and column types). Values are bound as parameters, except `IN`/`NOT IN`, pasted as written so a subquery works. Paging, sorting, filtering, and search re-run generated SQL (`table_view/sql.rs`) rather than manipulating an in-memory result, and all go through the staged-edit guard. DDL belongs to `schema_view`, not `table_view`.

**Completion.** `db/completion.rs` is pure — given the buffer, caret, `Catalog`, and engine, it decides what to offer, by tokenizing the statement rather than parsing it; `ui/completion.rs` adapts it to `gpui-kit`. The provider is asked on every edit and answers empty once the word ends, which is what closes the menu on a space. With `Tab` as the accept key, `QueryEditor` catches it in the capture phase and routes it as the menu's `Enter`. The menu positions from the previous frame's caret, so `follow_caret` asks for an extra draw.

**Running SQL.** `statement::split`/`at_cursor` let `Cmd+Enter` send only the statement under the caret (a selection runs verbatim). Every run returns a `Vec<QueryResult>`. A lone `SELECT`/`WITH … SELECT` from a query tab gets the tab's implicit `LIMIT` via `statement::with_limit` (scripts and `EXPLAIN` never do). `runtime::spawn` returns a `Task` whose abort handle the tab holds; cancelling drops the work and resolves the awaiting side with a "Cancelled" error.

**Query tabs run on a pinned connection.** A query tab's runs go to `db::pinned::PinnedConnection`, not the pool, so a `BEGIN` in one run and the `COMMIT` in the next reach the same server session and `SET`/`USE`/temp tables/`LOCK TABLES` persist. The pool stays for everything the app generates. The connection is checked out lazily, never returned to the pool (so whatever a tab left open is rolled back by the server), dropped on database switch and reconnect, and discarded if a statement is dropped mid-flight (`PinGuard::fetch`'s `Flight`); `cancel` asks the server to stop it by backend id. `PINNED_MAX` pins are allowed on top of the pool, and one more is refused rather than left waiting. `TxnState` is read back after every run (Postgres `now() <> statement_timestamp()`, SQLite `sqlite3_get_autocommit` — the one `unsafe` call, MySQL followed from the statements themselves in `pinned::mysql_after`). Closing a tab/connection or switching database asks before rolling back an open transaction. Transaction control is not a write to `statement::first_write`, so `BEGIN` works read-only and raises no `ConfirmWrites` question.

**Scripts** (`db/script.rs`'s `ScriptRun`) run on the pinned connection in a `ScriptMode` (`Transaction`, with a savepoint per statement so one failure can be undone alone, or `Autocommit`) with an `OnFailure` of `Ask` or `Skip`. The run is driven a step at a time: `start`/`resume` return `Step::Paused(run, failure)` and the session asks and resumes with a fresh `runtime::spawn`, so nothing on the Tokio runtime ever waits on the UI (which also lets the inline test `spawn` drive it). A paused run is parked on the tab; closing or cancelling gives it up on the runtime so its transaction is rolled back. `script::transaction_blocker` finds statements a transaction cannot hold (own `BEGIN`/`COMMIT`, MySQL implicit commits, `VACUUM`, …) and the run asks before going without one. A run started inside the tab's open transaction never begins its own: `Transaction` becomes a savepoint, and `Autocommit` joins it (still a savepoint per statement, so a Postgres failure cannot abort the tab's transaction), refusing a blocker outright. On MySQL, `Dedicated::execute` uses the text protocol (`sqlx::raw_sql`) and `fetch` falls back to it on error 1295, because the prepared protocol refuses `BEGIN`, `SAVEPOINT`, `LOCK TABLES`, and `USE`.

**The query console** is a read-only record of every statement the connection sent. `db/query_log.rs` is a GPUI-free ring buffer held on `Connection`; each shared entry point times itself and calls `Connection::log`, so nothing upstream knows it exists. User SQL is told from the app's own reads by a source tag, not a parameter: `run_query_with`/`execute`/`execute_script` log `Internal`, `ScriptRun`/`explain`/the pinned path log `User`, agent reads log `Agent`. A statement carrying a password goes through `execute_logged_as`, which logs a `********` stand-in. `import_dump`/`rebuild_table` run outside the pool and are not logged. Because `db/` cannot wake a view, the console, process list, server variables, query digest, and connection info are all **pull-based**: built once, refreshed on open, on a database switch, and by their own Refresh button.

**Server tools** (process list, server variables, query digest, connection info; SQLite maintenance is the SQLite-only counterpart) each pair a `Connection` method with per-engine SQL constants and mostly reuse `DataGrid` over a plain `QueryResult`. Things to know: they are hidden and never called for SQLite where there is no server to ask (`Tool::offered`); ending a process always asks first, independent of `SafetyMode`, and MySQL's `KILL` takes a pasted parsed integer because a bound `KILL ?` answers with a packet sqlx cannot decode; server variables filter client-side (`filter_variables`); the query digest checks that the instrumentation is on and answers `QueryDigest::Unavailable(reason)` shown as a banner, not an error; SQLite maintenance's task list is closed and `Maintenance::writes` is its own list because `PRAGMA optimize` reads as a plain pragma to the classifier — the longer-term pragma management is meant to grow out of that tab.

**The Agents panel** (`ui::agents::AgentPanel`, `db/agent/`) is a chat scoped to a session's connection that talks to a user-configured OpenAI-compatible endpoint. It makes no model call until a message is sent and an endpoint is set. The thread is in memory only — never in `workspace.json` — since it can hold schema, rows, and pasted secrets; the system prompt never holds a password or key. `db/agent/` is GPUI-free, and `gate.rs` decides what may run **in code, not in the prompt**. Three gates guard a write and none implies another: `ConnectionConfig::agent_access` (whether the tool exists at all), the connection's `SafetyMode`, and its `WriteApproval`; `gate::write_decision` is the one place they meet, and `gate::FORBIDDEN` refuses file-system/server-process statements at any level, as the per-engine function denylist in `gate::classify` refuses side-effect functions (`pg_terminate_backend`, advisory locks, `dblink`, `SLEEP`, …) anywhere in a statement — a read-only session stops writes to rows, not those. Every agent read goes through `Connection::run_query_as_agent` on a dedicated connection the *server* holds read-only, because the classifier cannot see a function that writes behind a `SELECT`. Every agent write goes through `Connection::execute_as_agent` on a dedicated connection that closes afterwards, because sqlx resets no session state when a connection returns to the pool, so a Full-access `SET`/`USE`/`PRAGMA`/temporary table would otherwise reach the app's later pooled work. A read is bounded twice: `statement::clamp_limit` rewrites the `LIMIT` where it can, and the read itself stops one row past the cap whatever the SQL says, closing the connection rather than draining the rest.

**Backups** (`db/backup.rs`) shell out to `pg_dump`/`mysqldump`, one invocation per selected database. The password never reaches a command line or normally the environment: it goes in a temporary credentials file the run creates and deletes, and tool output is redacted against it. MariaDB's client (no `--ssl-mode`) is detected and its arguments rewritten; the SSH tunnel address is used when there is one.

**Dashboards and charts.** A query tab's result can be charted; a chart is rebuilt from the result on every draw, and rows that do not read as numbers are skipped and counted rather than plotted as zero. A dashboard stores no results: it runs its widgets on open and Refresh through the query tab's path (variables, implicit limit), but only ever reads, whatever the connection's `SafetyMode`, since every refresh would repeat a write: `Connection::run_read_with` refuses anything the classifier does not recognise as a read and runs the rest in a server-side read-only session, as an agent read does. A widget that fails or writes is its own error cell.

**Query results** flow through `db::query::QueryResult` (columns + rows of `Cell` + elapsed time + server `messages`) into `ui::data_grid::DataGrid`, a virtualized grid. `QueryResult::affected` is filled in for writes because `fetch_all` reads rows and `rows_affected` from the same stream.

**Exporting and copying.** `db/export.rs` is plain text with no window and no database. JSON is typed by the driver's column type (an integer past 2^53 becomes a string); SQL writes a number bare only for numeric columns, and `quote_literal_for` doubles a backslash on MySQL only. `TableView::select_sql(paged: false)` drops `limit`/`offset` so an export is every row the view is showing. `DataGrid::snapshot(scope, cx)` is the one place that decides what a copy or export takes, staged edits included; copies are capped (100,000 rows / 50 MB) and the notice says so rather than pretending to be whole. Items that need something the grid lacks are hidden or disabled rather than left to fail.

**Importing.** `db/import/` streams a SQL dump into the connection one statement at a time, never held in memory, on one dedicated connection (closed rather than returned to the pool, so a cancelled import leaves no half-open transaction and `SET`/`USE`/temp state survives the run). The dump's own top-level `BEGIN`/`COMMIT` are replaced by the runner's, and `OnError` decides a failure's effect (`Rollback` falls back to `Stop` on MySQL, whose DDL commits itself). The dialog pre-flights the file and blocks a read-only connection.

**Schema editing.** `schema_view` stages a `Change`: `Statements` run one at a time, while `Rebuild` is one atomic procedure via `Connection::rebuild_table` for SQLite, whose `ALTER TABLE` can only rename/add/drop (sqlite.org's "Making Other Kinds Of Table Schema Changes"). The rebuild runs on one dedicated connection with foreign keys off around a transaction (`PRAGMA foreign_keys` is a no-op inside one), `PRAGMA foreign_key_check` before commit, and `legacy_alter_table = ON` so the rename survives a view left dangling mid-procedure. A table holding something `TableSchema` cannot model (`CHECK`, `COLLATE`, generated columns, `AUTOINCREMENT`, `WITHOUT ROWID`/`STRICT`) is refused rather than silently changed. The structure tab's `SQL` view shows the object's definition: read from the catalog on SQLite/MySQL, generated from catalog rows on Postgres.

**Query plans.** `db/plan.rs` reads each engine's `EXPLAIN` output into one `Plan` tree, falling back to raw rows when the shape is unexpected (`Explained::Rows`). `EXPLAIN ANALYZE` runs the statement, so on a connection that is neither read-only nor auto-apply the session asks first.

**Settings.** `settings::Settings` is one serde struct behind a GPUI global; `settings::update` is the only way to change it (it writes the file, re-applies the theme, refreshes windows). `apply` also re-runs `apply_scrollbars` because `Theme::change` rebuilds what they read. Every setting needs a way in that is not a keystroke (the Settings… menu item).

**Tests.** `src/ui/tests/` and `src/db/tests/` are one file per area, with every shared fixture in `mod.rs` (even one only a single file uses, so the next area can find it) and each file opening with `use super::*;`. Put a new test in the file that matches what it is about. Pure unit tests sit beside their module. `db/tests/classifier.rs` holds the write corpus (a classifier bug adds a row there first) and the `proptest` properties over the scanners; `proptest-regressions/` is committed. Live-server tests are `#[ignore]`d, live in `db/tests/live.rs`, and name their container in a doc comment.

## Accessibility

* Every icon-only `Button` and bare `Checkbox` carries `.accessibility_label(...)`.
* Where an action has a keybinding, use `.tooltip_with_action(text, &Action, Some("Context"))` rather than `.tooltip(text)`, so the bound key is shown.
* Anything clickable is a `Button` (tab-reachable, answers the keyboard), or for a list a `gpui-kit` `Tree`/`TreeState` (see the sidebar object list).
* Nothing is told by colour alone: errors say `Error: …` in words, staged cells are underlined, deleted rows are struck through.
* The grid's per-row pick boxes are not tab stops (one per row would mean tabbing through a page); `Space`, `Shift`+arrows, `Cmd+A`, and `Cmd+Shift+A` pick rows from the keyboard.
* Known deviation: the connection editor's Connect split button has an unnamed caret half — `gpui-kit`'s `DropdownButton` exposes no label for it. Its one item (connect without saving) is not reachable any other way yet.
* Known deviation: a dock panel's own `+` is not tab-reachable — `gpui-kit`'s dock forces `tab_stop(false)` on toolbar buttons. `Cmd+T` and File › New Query Tab cover it.
